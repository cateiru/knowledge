# クロールした作品が、配信サイト側の ID の振り直しで重複登録される

漫画配信サイトをクロールして作品を DB に登録していると、URL が違うだけで中身が同じ作品が別の行として増えていくことがある。2026年11月に、この重複を調べて掃除したときの手順と判断をまとめる。

## 前提

- 作品の行は `(source_key, viewer_url)` を一意キーにして upsert している。
- 一覧から消えた作品も行は消さず、最後に見つけた日時（`last_seen_at`）の更新が止まるだけにしている。
- 作品にはユーザーのジャンル投票と、AI が自動で付けたジャンル（`is_ai_generated = true` の行）がぶら下がっている。

## 原因: サイト側が ID を振り直す

コミチ（comici）のプラットフォームで動いているサイトでは、同じ記事でも次の 2 段階で識別子が変わることを確かめた。

1. 記事のページの URL（`/episodes/<hash>`）のハッシュだけが変わる。
2. 記事 ID（HTML の `data-log-article-id`）そのものが別の値で振り直される。

1 は、URL ではなく記事 ID を安定した識別子として持てば防げる。ただし 2 が起きると記事 ID も変わるので、この対策では防げない。実際に 2026年9月から11月の約2か月で、5 サイト・15 作品ぶんの重複がたまっていた。

振り直しのときに、掲載日やタイトルまで変わることがあった。

- 掲載日が数週間ずれて登録し直された作品があった。
- タイトルに「【ネーム版】」が付いて改題された作品があった。説明文・掲載日・サムネイルはまったく同じだった。

## 重複を見つける

同じ配信サイトの中で、タイトルと作家が一致する行を探す。

```sql
SELECT source_key, title, author, count(*)
FROM <items>
WHERE title IS NOT NULL
GROUP BY source_key, title, author
HAVING count(*) > 1;
```

タイトルが変わっている場合はこれでは見つからないので、サムネイルの URL が一致する行も探す。

```sql
SELECT source_key, thumbnail_url, array_agg(id ORDER BY id), array_agg(DISTINCT title)
FROM <items>
WHERE thumbnail_url IS NOT NULL
GROUP BY source_key, thumbnail_url
HAVING count(*) > 1;
```

どちらも、重複ではないものが混ざる。目で確かめてから掃除の対象にする。

- 前後編や再掲で、掲載日が違う別のエピソードになっているもの。
- 「前編」「番外編1」のように、作品名ではなく話の名前がタイトルとして取れてしまっているもの。作家が違えば別の作品になる。
- 賞の名前だけが違う、サムネイルを使い回した別の作品。
- 連作の読み切りで、一覧のリンクが最新話に差し替わるたびに行が増えているもの。毎話を別の読み切りとして扱うかどうかは、サービスの方針で決める。

本物の重複は、古い方の行の `last_seen_at` が、新しい方の行の登録日あたりで止まっている。これが判断の目印になる。

## 掃除する

それぞれの作品で、今も一覧に出ている行（一番新しい行）を残し、古い行を消す。古い行に付いている投票を失わないように、次の順で 1 つのトランザクションにまとめて実行した。

1. 人間の投票を受け取る行から、AI のジャンル判定の行を消す。人間の投票が付いたら AI 判定は使わない、という投票 API の動きに合わせるため。
2. 古い行に付いている人間の投票を、残す行に付け替える。
3. 古い行に残った AI のジャンル判定の行を消す。
4. 古い行を消す。

```sql
BEGIN;

DELETE FROM <votes>
WHERE is_ai_generated AND item_id IN (<投票を受け取る行の id>);

UPDATE <votes> v SET item_id = m.keep_id
FROM (VALUES (<古い id>, <残す id>), ...) AS m(old_id, keep_id)
WHERE v.item_id = m.old_id AND NOT v.is_ai_generated;

DELETE FROM <votes> WHERE item_id IN (<古い行の id>);

DELETE FROM <items> WHERE id IN (<古い行の id>);

COMMIT;
```

これは本番のデータを消す、取り返しのつかない操作。実行する前に、次のことを確かめておく。

- 投票には `(item_id, genre_id, user_id)` の一意制約があるので、付け替えると衝突することがある。同じ人が古い行と残す行の両方に同じジャンルで投票していないかを、先に数えておく。今回は 0 件だった。
- 投票のほかに、作品の行を外部キーで参照しているテーブルがないか。
- `RETURNING` を付けて、消えた件数・付け替えた件数が事前の見込みと合っているか。

## 別のサイトに同じ作品が載っている場合

同じ出版社が運営する別のサイト（例: となりのヤングジャンプとヤンジャン＋）に、同じ作品がそれぞれ載っていることがある。今回は数百作品が重なっていた。

「姉妹サイトで同じパスの URL があれば片方の登録を飛ばす」という仕組みを入れていても、これは防げない。ドメインも URL の形も違い、パスが一致しないからである。1 枚にまとめるか、サイトごとに表示するかはサービスの方針によるので、今回は手を付けていない。
