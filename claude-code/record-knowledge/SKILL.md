# knowledge リポジトリに知識を書き留める

作業で得た知識を `git@github.com:<owner>/knowledge.git` に書き留め、`main` に push する。このリポジトリは **public** なので、非公開情報を書かないことが最優先。

## 手順

1. **リポジトリを用意する**
   - `~/repositories/knowledge` がなければ clone する。あれば `git pull --ff-only` で最新にする。
2. **ルールを読む**
   - リポジトリの `AGENTS.md` を読み、構成と書き方のルールに従う。このスキルと食い違う場合は `AGENTS.md` を優先する。
   - `README.md` と既存のファイルを見て、同じテーマのファイルがあれば新しく作らずにそこへ追記する。
3. **書く**
   - この会話で実際に確かめたことだけを書く。推測や見積もりは、そうと分かるように書く。
   - コマンドだけでなく、なぜそうするのか、何に注意するのかを書く。うまくいかなかった方法とその理由も残す価値がある。
   - 具体的な値は `<pkg>` や `/path/to/...` のような置き換え用の表記にする。
   - 新しいファイルは `README.md` の一覧にリンクを追加する。
4. **非公開情報が混ざっていないか確かめる**
   - 次のような情報は書かない。
     - API キー、トークン、パスワードなどの認証情報
     - ホスト名、ホスト ID、IP アドレス
     - メールアドレス、本名、ユーザー名を含むパス
     - ミラーや社内サーバーの URL
     - 私的なリポジトリ、サービス、コンテナの名前
     - ハードウェアの型番など、書く必要のない環境の詳細
   - この会話に出てきた具体的な値（ホスト ID、ユーザー名、パス、サービス名など）を grep して、含まれていないことを確かめる。
   - 設定ファイルを確認するときは、認証情報を表示しない。
5. **commit して push する**
   - commit メッセージは日本語で書く。1行目に要約を書き、必要なら空行のあとに箇条書きで詳細を書く。
   - harness から指示された attribution の行があれば末尾に付ける。
   - `main` に push する。
6. **報告する**
   - 追加・更新したファイルと commit を短く伝える。
   - 書かなかった非公開情報の種類も伝える。
