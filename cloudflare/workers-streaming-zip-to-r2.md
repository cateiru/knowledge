# Workers で大きな zip を R2 へ少しずつ書き出す

2026年11月に、Cloudflare Workers（OpenNext の Next.js アプリと Workflows）で、記録の CSV と写真・動画を zip にまとめて R2 に置く処理を作ったときのメモ。zip の書き出しはライブラリを使わずに自前で書いた。

## 方針

- Worker のメモリは 128 MB までなので、写真・動画を全部読み込んでから zip にすることはできない。R2 から読んだ順に zip のバイト列を作り、そのまま R2 に流す
- R2 の `put` にストリームを渡すときは長さが分かっている必要がある（`FixedLengthStream` など）。長さを先に決めない代わりに、マルチパートアップロード（`createMultipartUpload`・`uploadPart`・`complete`）で書く
- 写真・動画はもう圧縮されているので、zip は圧縮しない（STORE）。CPU を使わず、zip 全体の大きさも事前に計算できる

## マルチパートアップロードのパートの大きさ

- パートは最後以外を 5 MiB 以上にする。大きさをそろえておくと安全なので、固定の大きさ（例: 8 MiB）のバッファにためて、いっぱいになったら `uploadPart` する
- 最後のパートは 5 MiB 未満でよい。パートが 1 つもないと `complete` できないので、空でも最後に 1 回は送る
- 失敗したら `abort()` してから例外を投げる

```ts
const upload = await bucket.createMultipartUpload(key, {
  httpMetadata: { contentType: "application/zip" },
});
const parts: R2UploadedPart[] = [];
let buffer = new Uint8Array(PART_SIZE);
let filled = 0;
const flush = async () => {
  parts.push(await upload.uploadPart(parts.length + 1, buffer.subarray(0, filled)));
  buffer = new Uint8Array(PART_SIZE); // 送ったバッファは使い回さない
  filled = 0;
};
// zip のバイト列を受け取るたびに buffer にコピーし、いっぱいになったら flush する
```

## データ記述子を使わない

最初は、ストリームを読み終えるまで CRC が分からないので、ローカルファイルヘッダーの CRC・大きさを 0 にして、中身のあとにデータ記述子（汎用フラグの bit 3）を書く形にした。

この zip は Python の `zipfile` や、ファイルとして開いた `bsdtar` では展開できた。しかし `cat out.zip | bsdtar -tvf -` のように先頭から順に読むと、データ記述子を使ったファイルの大きさが 0 になった。圧縮しない（STORE）ファイルでは、中身の終わりを中身から判断できないためで、順に読むツールでは展開できない。

そこで、どのファイルも CRC と大きさをローカルファイルヘッダーに書く形にした。CRC は中身を書く前に必要なので、次のようにした。

- CSV のように先にメモリに持っているものは、そのまま CRC を計算する
- R2 の写真は、小さいもの（例: 16 MiB 以下）は `arrayBuffer()` で読んで CRC を計算する
- 大きい動画は、1 回目に読んで CRC だけを計算し、2 回目に読んで zip に流す。2 回目に読んだ大きさが 1 回目と違えば、壊れた zip にならないよう例外にする

## ZIP64 を使わないなら、書く前に大きさを確かめる

ZIP64 を使わない zip は、全体の大きさ（オフセット）が 4 GiB、ファイル数が 65,535 までしか書けない。STORE でデータ記述子もなければ、zip の大きさは次の式でちょうど決まるので、書き始める前に上限を超えるかを判定できる。

```text
22（終端） + 各ファイルの (30 + 名前のバイト数 + 中身の大きさ + 46 + 名前のバイト数)
```

上限を超えるときは、作り始めずに「大きすぎる」として失敗にした。書いている途中でも、オフセットが上限を超えたら例外にしておく。

## そのほか

- ファイル名を UTF-8 で書くときは、汎用フラグの bit 11 を立てる。展開する環境によっては文字化けするので、zip の中のファイル名は英数字にした
- CSV は Excel で文字化けしないよう、先頭に BOM（`﻿`）を付けた
- CRC-32 は `"123456789"` が `0xCBF43926` になることで確かめられる
- テストでは、書いた zip のセントラルディレクトリから各ファイルを読み、ローカルファイルヘッダーの名前・CRC・大きさと一致すること、中身の CRC が合うことを確かめる小さな読み取り関数を書いた
