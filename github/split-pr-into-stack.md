# 完成した大きな PR を積み上げ PR に分割する

実装とレビューが終わった大きな PR を、あとから積み上げ PR (前の PR のブランチを base にした PR の列) に分けたときの手順と注意点。2026年11月に、81 ファイル・約 4,300 行の PR を 7 本に分けて確かめた。

## 境目の決め方

「単独でマージ・デプロイしても壊れない」順に並べる。1 本 150〜1,000 行程度になった。

1. どの画面からも使わない共通部品
2. マイグレーション・テーブル・ユースケース
3. 既存の保存・読み取りへの組み込み (見た目は変えない)
4. 画面 (ユーザーが使い始められる最小の範囲)
5. 管理画面
6. 波及する表示や出力
7. 外部向けの API

注意したこと。

- 新しいテーブルを参照する文 (親の削除と一緒に消す処理など) が最初に入るのはどの PR かを調べ、マイグレーションの適用期限をその PR の本文に書く。画面を変える PR より前になることがある。
- 「全部入れ替える」形の更新 (紐付けを消してから入れ直すなど) を先に入れるときは、まだ値を送らない呼び出し元が、後の PR で付いた値を消さないようにする。API の編集のように省略できる入力では、今の値を読んで引き継ぐ処理を同じ PR に入れ、テストを足す。
- 一覧・説明・リリースノート・ヘルプは、機能と同じ PR に入れる。「画面や項目を変えたらヘルプも更新する」という規約がある場合、分割するとレビューは PR ごとの差分で規約を判定するため、大きな PR では見逃された更新漏れが指摘される (実際に 2 件見つかった)。

## 作り方

元のブランチの履歴 (作り直しを含む) は使わず、最終状態のファイルから作り直すと速い。

```sh
F=<元の PR の最新コミット>
git switch -c <prefix>-1-<name> origin/main --no-track
git checkout "$F" -- path/to/files-for-this-pr
# 複数の PR にまたがるファイルは、最終状態から後の PR の部分を取り除く
git commit

git switch -c <prefix>-2-<name>   # 前のブランチの上に積む
git checkout "$F" -- path/to/next-files
```

最後のブランチで差分を見て、意図した違い (バージョンやリリースノートなど) だけが残っていれば、取りこぼしがない。

```sh
git diff --stat HEAD "$F"
```

- またがるファイルは「最終状態から削る」と、最後の PR で `git checkout "$F" -- <file>` するだけで元に戻る。前から順に足していくより間違えにくい。
- 途中のブランチでも、lint・型・全テストを流す。後の PR の関数を import しているなどの漏れは、最後のブランチだけを確かめても分からない。
- E2E も、その PR までの範囲に削った版を途中のブランチで流す。後片付け (作ったデータの削除) を後の PR の画面に頼っている場合は、ローカルの DB に残るので消す。
- zsh では `$F:path` が修飾子として解釈される (`$F:s...` は置換)。`"${F}:path"` と書く。また、変数に入れたコマンドは単語に分割されないため、`$CMD arg` の形では動かない。

## PR を作った後

- 本文に積み上げの順番を書く。番号は作ってみないと分からないので、先に全部作り、番号がそろってから `gh pr edit --body` で書き足す。
- issue を閉じるキーワード (`Closes #...`) は最後の PR だけに書く。途中の PR に書くと、そこでマージした時点で閉じる。
- 下の PR を直したら、上のブランチへ順にマージで取り込む。push 済みの履歴を書き換えないで済み、各 PR の差分はその PR の変更だけのままになる。
- 上の PR が下の PR の修正を取り込むマージコミットにも、Codex の自動レビューが走る。30 分反応がないものには `@codex review` とコメントすると、その後に 👍 が付いた。
- 比較元を git の履歴から探す VRT (reg-suit) は、一部の PR で全件「新規」になり、差分が 0 件でも何も比べていなかった。同時に push したため、下の PR の VRT がまだ終わっていなかったのが原因とみられる (未確認)。
