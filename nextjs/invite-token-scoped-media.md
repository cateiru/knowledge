# メンバー限定の画像を、招待された人にだけ招待のトークンで見せる

2026年11月に、家（グループ）への招待ページに「誰から招待されたか」として招待した人のアイコンを出したときのメモ。

## 困ったこと

ユーザーのアイコン画像は、同じ家のメンバーにしか見せない認可にしていた（`/media/<id>` の配信で、見る人と画像の持ち主が同じ家にいるかを確かめる）。
招待された人はまだ家に参加していないため、招待ページで招待した人のアイコンを `/media/<id>` で読むと 404 になり、代わりの人のアイコンしか出ない。

画像の認可を「ログインしていれば誰でも」に広げるのは、アイコンを見せる相手を絞っている意味がなくなるので避けた。
招待は参加するまで招待された人を記録していないため、「この人宛ての招待があるか」で認可することもできない。

## やったこと

招待のトークンを含む専用の配信ルートを作り、トークンが「まだ使える招待」のときだけ、その招待を作った人のアイコンを返す。

```text
GET /invitations/<token>/inviter-icon?v=<画像の ID>
```

- ルートの中で、招待ページと同じ処理（トークンのハッシュで招待を引き、期限切れ・使用済み・すでにメンバーかを判定する）を呼び、「参加できる」状態のときだけ画像を返す。それ以外は 404 にして、招待の有無を明かさない。
- 返す画像は「招待を作った人の、今のアイコン」に限る。URL で画像の ID を受け取って、それを返すようにはしない（任意の画像を読めてしまうため）。
- ログインは必須のまま。トークンだけで見せると、URL を知っているだけの人にも見えてしまう。
- 画像の配信は長期の `immutable` キャッシュにしていたため、URL が同じだとアイコンを変えても古い画像が出続ける。URL に `?v=<画像の ID>` を付け、アイコンが変わると URL も変わるようにした（ルートの側では `v` を使わない）。
- URL にトークンが入るので、レスポンスに `Referrer-Policy: no-referrer` を付けた。ページの側も `referrer: "no-referrer"` にしていた。

## 確かめたこと

ローカルで、招待した人に一時的にアイコンを設定して、次のようになることを確かめた。

- 参加できる招待のトークン: 200 で画像が返る。
- 招待された人がすでにメンバーの家の招待・存在しないトークン: 404。
- ログインしていない: ログイン画面へのリダイレクト（ミドルウェアの扱い）。

## 注意

- Next.js の `route.ts` からは、`GET` などのハンドラー以外の関数を export しない。URL を組み立てる関数はページの側に置いた（ルートのファイルからの余計な export は、ビルドの型チェックで弾かれることがある）。
